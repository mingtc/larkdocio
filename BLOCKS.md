# BLOCKS.md — larkdocio block-support matrix

**The single source of truth for how larkdocio's reader treats every Lark (Feishu) docx
block type.** This file is **current-state only** — no history, no roadmap. It is verified
against the live registry (`src/larkdocio/blocks/`, `blocks.get_registry()`) and the tests
(`tests/test_registry.py`, `tests/test_conformance.py`, `tests/test_parser_warning.py`),
**not** against any prose reference. If a row disagrees with the code, the row is the bug.

> **Citations into `dev/`, `progress/` and `requirements/`** in this file are provenance
> notes **in the dev repo**, pointing into the maintainers' private records, which the public
> repository does not carry. Read each as provenance for the fact stated beside it.
> A recorded API response is cited at its `tests/captures/…` copy where the repository carries
> one; a recording cited under `dev/` is a maintainers' record the repository does not carry.

> "What it emits" is the Markdown the **reader** produces for that block, and **Status** is
> its read disposition. The **Write** column is the block's **write-support** state — what
> the docx write engine can do to it (§ Write-support vocabulary). Handler-authoring
> mechanics (how to add a type) live in
> [`src/larkdocio/blocks/BLOCK_TYPES.md`](src/larkdocio/blocks/BLOCK_TYPES.md); **status lives
> only here.**

## Status vocabulary

| Status | Meaning |
|--------|---------|
| **rendered** | A registered `@register_block(N)` handler converts the block to Markdown. |
| **placeholder** | A registered handler emits a fixed, traceable **marker** instead of the block's real content, because that content is not reachable/representable. |
| **intentionally-skipped** | **No handler, by documented decision.** The parser logs `Unknown block type N …`, drops the block's OWN content, and renders its children transparently (the unknown-type fallback below). Deliberately unsupported **for a stated reason**, one of: **superseded** by another handled type (diagram 21 / mindnote 29 → Board 43), **re-serialized** as a different handled type (link_preview 48 → iframe 26), an **embedded data source / external-service reference** with no meaningful flat-Markdown form, or a **feature-gated type with no live payload** (a handler would be speculative until one appears). Each such row carries its rationale in the matrix (the read-completeness spec § Decision f). |
| **unregistered-warns** | **No handler (not yet supported).** Same `Unknown block type N …` warning + transparent-children fallback as above. Not a deliberate exclusion — simply unhandled today. |

**Runtime note (the unknown-type fallback):** `intentionally-skipped` and `unregistered-warns`
are **indistinguishable at runtime** — both hit the parser's fallback branch, which logs the
identical `Unknown block type N …` warning (`src/larkdocio/read/parser.py`) and then renders the
block's **children transparently** — each child by its own handler, at the unknown block's own
depth, with **no markup of the unknown block itself** (the `view`/`grid` own-depth-recurser
precedent; LD-045). So an unknown **container** surfaces its subtree
instead of dropping it behind one warning (the agenda / file-in-view silent-subtree-drop class);
a **leaf** unknown (no children) still emits nothing. The block's own attributes are always
dropped — only the subtree is preserved. The difference between the two statuses is **intent**,
recorded here so a maintainer knows whether an unhandled type is a decision or a gap.

## Write-support vocabulary

The **Write** column: what the docx **write** engine (`src/larkdocio/write/`) can do to a
block of this type. It is a *different axis* from Status — a type can be perfectly readable
and still uncreatable — and it exists because an op name cannot express the difference
(dogfood **F2**: "insert" existed but no heading was creatable; **F9**: a table's cells were
editable while a table was not creatable — closed by LD-134 / LD-135, with the **merge**
case as the surviving editable-≠-creatable nuance).

| Write | Meaning |
|-------|---------|
| **creatable** | The engine can bring a block of this type into **existence** through the plan-gated `dry_run` → `Plan` → `apply` path (never a raw payload) — either because a `NewBlock` kind maps to it, or because it is provisioned **with its parent** (a `table_cell` (32) has no kind of its own: on the one-call route the engine sends the whole table subtree — grid, cells and cell text — in a single `descendant` call, and on the create-then-fill route Lark creates the R×C grid from the table's property and the engine fills each cell). Created content is **unstyled text** — with one exception, the **link anchor**, which a paragraph-family block carries via `NewBlock.rich_paragraph` and a **table cell** via a `TextSpan` sequence in `rows=` (LD-619); a creatable text-bearing block's text is editable too. A type can be creatable in its plain form while a *variant* of it is not — an authored table is always a plain grid, because **merged cells (colspan/rowspan) are not expressible in Markdown** and are refused (`merge-not-expressible`), never approximated. |
| **editable** | **Not creatable, but writable:** a shipped edit op patches this block's text while no op brings a block of this type into existence. The **editable ≠ creatable** nuance (F9) this slug exists for is now carried by the *merge* case rather than by tables as a whole: since LD-135 a plain table **is** creatable, but a **merged** table only reads and (for its unmerged cells) edits — no merge can be authored. No row currently carries this state. |
| **creatable-out-of-band** | The engine can bring this type into **existence**, but **not through the plan-gated path** — it needs *bytes* and a network call the Markdown compiler has neither of, so it is created by a dedicated op instead of by a `NewBlock` kind. Today that is **image (27)** and the **file attachment (23)**, through `larkdocio.write.media.put_image_in_document` / `put_file_in_document`, which performs the three calls the route actually requires — create the empty image block, upload the bytes **bound to that block**, then `PATCH replace_image` to bind them — and takes the **read-back** as the verdict, because the upload answering success is *not* a bind. `compose()` still refuses a Markdown `![](…)`: the compiler holds no bytes. The rows in this state are pinned against `larkdocio.write.media.OUT_OF_BAND_CREATABLE_BLOCK_TYPES` the same bidirectional way `creatable` is pinned against the encoder. |
| **not-creatable** | The engine cannot bring this type into existence. Some are **write-hostile** (board 43, embeds 18/26/30/53, synced 49/50 — they hold no patchable text and refuse an edit outright, `WRITE_HOSTILE_NODE_TYPES`); the rest are simply outside the creatable set in this rung. |

**`WRITE_HOSTILE_NODE_TYPES` lists what refuses an EDIT, not what can be created** — the two
are different questions, which is why image (27) sits on that list *and* in
`creatable-out-of-band` without contradiction: a new image block can be authored, while no op
edits an existing one's content in place (changing an image means create another and delete
the old). Verdict re-examined when the image op shipped and left **unchanged**; the guard is
in `tests/test_blocks_md_matrix.py`.

**Every state in this column is gated, and the gate is document-wide.** Whatever the Write
column says a type allows, it happens only through the plan-gated `dry_run` → `Plan` → `apply`
path, under **two** staleness guards: per-anchor `STALE_ANCHOR` (the anchored block is re-read
and re-validated right before its own write) **and** the whole-document `STALE_DOCUMENT`
compare-and-swap (LD-139 — a plan may carry the document's `revision_id`, and if
the document changed before the batch runs, the **entire** batch refuses with **zero writes
issued**, never a partial application and never a re-located anchor). So `creatable` never
means "created wherever it lands": a block of a creatable type is created **at the previewed
position in the previewed document**, or not at all. The document guard is what covers drift
*around* an anchor, which `STALE_ANCHOR` cannot see.

**No block-type mutation, ever.** No op promotes an existing block to another type — a
paragraph never becomes a heading. `creatable` means *a new block of this type*, and the
creatable set is **structurally closed**: `NewBlockKind` is a closed enum and `NewBlock`
carries no block-type escape, image token, embed url or sheet reference, so a
`not-creatable` type is not merely refused at runtime — it is **inexpressible**. The
`creatable` rows are pinned against code truth (`larkdocio.write.encode.CREATABLE_BLOCK_TYPES`)
by `tests/test_blocks_md_matrix.py`, so a creatable kind added without its row — or a row
claiming a creatability the encoder lacks — reddens the suite.

## Read-lossiness vocabulary

The **Read-lossiness** column: *how* lossy the reader's Markdown is for a block of this
type. A third axis — "is type N handled"
(Status) and "what does it emit" were already here, but the question a consumer actually
has is **"will my callouts / images / boards survive the read?"**, and neither of the other
two columns answers it. It is a **state, not a boolean**, because "lossy" is the same word
for a heading that comes back one level shallower and for a whiteboard whose pixels are a
separate file — both lossy, planned for differently.

**It is about the MARKDOWN PROJECTION only.** The node tree (`parse_docx_tree`) is the
full-fidelity level; a type that reads lossily into Markdown still arrives whole there.

| Read-lossiness | Meaning |
|----------------|---------|
| **full** | The block's text and its structure both come through into the Markdown. What is left out is only what Markdown has no form for at all — a run's colors, a block's alignment, the review anchors on it — and each of those is on the node tree (the consumed-into-model / dropped-at-render doctrine). |
| **projected** | The content comes through in a **different shape** than the block's own, so reading the Markdown cannot tell you the original shape: a merged table serialized as HTML (pipe tables have no spans), an H7–H9 capped to `######`, a layout container flattened, a diagram add-on emitted as its source text in a fence. |
| **out-of-band** | The content is not text and does not travel in the Markdown at all: the reader downloads it as a separate file (`static/`) and the Markdown carries a link. |
| **reference-only** | A traceable marker naming the block and its id is emitted instead of the content, because the content lives where this read does not go — another document, a separate service, or a binary this read does not fetch. Emitting the marker is the deliberate alternative to a silent drop (LD-048). |
| **not-handled** | No registered handler. One `Unknown block type N …` warning, nothing of the block's own emitted, children rendered transparently — so an unhandled **container** surfaces its subtree while an unhandled leaf emits nothing. Exactly the set of types with no registry key, never a judgement. |

**This column is what the wheel carries.** `/BLOCKS.md` is a repo-root document
`package-data` cannot reach, so the three read answers are projected into
`larkdocio.capabilities(full=True)["surfaces"]["docx-read"]["block_read_support"]` — `handled` off
the live registry, the name / emission / lossiness off
`larkdocio.blocks.read_support.READ_SUPPORT`, which `tests/test_blocks_md_matrix.py` pins
**cell-for-cell** against the rows below, bidirectionally. Edit the row here; the guard
makes the shipped copy follow. A handler registered for a type with no row makes
`capabilities()` refuse to build.

## Round-trip projection vocabulary

The **Projection** column: when a document is projected for **round-trip editing**
(`larkdocio.model.project_block_ids`, which renders the same Markdown with one
`<!-- lark:block:<id> -->` marker per block), is a block of this type one an edit can be
applied back to, or one the projection only **conserves**? A **fourth axis**, and not a
restatement of Write: a table and a mermaid add-on are both `creatable`, and both are
`opaque` here, because the reader's Markdown for each is a *reshaping* of the block rather
than the block's own content.

| Projection | Meaning |
|------------|---------|
| **editable** | The projection's Markdown for this block is the block's own content in a shape the authoring dialect can compile back, so an edit to it is a change a reconciler can express as a request against this block. The marker is the bare `<!-- lark:block:<id> -->`. |
| **opaque** | The marker carries a kind — `<!-- lark:block:<id> opaque=<kind> -->` — and the block is **conserved**: either the authoring dialect cannot create a block of this type at all, or the reader renders it in a different shape than the block's own, so no edit to the Markdown could be applied back. The block's readable content is still shown; opaque means "do not reconcile me", not "hide me". |

**THE CONSERVATION CONTRACT.** An `opaque`-marked block is **left exactly alone** by any
reconciliation: it is **not edited**, **not deleted**, and **not re-created** — even if the
edited projection **omits it entirely**. Conservation is the default posture and destruction
is never inferred: the absence of a block from edited Markdown is evidence about the
Markdown, not an instruction about the document. **A table is opaque as a whole** and its
cells are not individually addressable through the projection; the supported route for
changing a cell is the **table-cell patch** path in `larkdocio.write`.

**This column is DERIVED, not authored.** `larkdocio.model.conservation` joins three things
that already know the answer — the live handler registry, `write.encode.CREATABLE_BLOCK_TYPES`,
and this file's own Read-lossiness column (as shipped in `blocks.read_support`) — and a type
is `editable` only when all three say yes. The rows above are pinned **bidirectionally**
against that derivation by `tests/test_blocks_md_matrix.py`, so the two sets stay
complementary and exhaustive and a newly supported type cannot fall through both. A block
type the reader has **no handler for** is opaque under the reader's own unknown-block
identity, `unknown-block-type-N` — the same type number its `Unknown block type N …` warning
names.

**How to read the enum:** integer → official Feishu docx block-type name
([Block data structure](https://open.larkoffice.com/document/ukTMukTMukTM/uUDN04SN0QjL1QDN/document-docx/docx-v1/data-structure/block)).
Every `rendered`/`placeholder` row maps to a real key in `blocks.get_registry()` (39 handlers);
every `intentionally-skipped`/`unregistered-warns` row has **no** registry key.

### Write-support summary

Each bullet leads with its block types in **one backticked span**, then explains itself —
the span is what `tests/test_blocks_md_matrix.py` parses, so this summary is pinned against
the rows above **and** against code (`larkdocio.write.encode.CREATABLE_BLOCK_TYPES` and
`capabilities(full=True)["surfaces"]["docx-write"]["content_constraints"]["creatable_block_types"]`)
in both directions. It used to say "creatable (15) … editable (2): 31 table + 32 table_cell"
for a whole tranche after LD-135 made both creatable — a summary contradicting its own rows
two screens away — which is why the count and the list are now guarded rather than trusted.

- **`creatable` (18):** `2, 3–11, 12, 13, 14, 15, 17, 31, 32, 40` — text (2),
  heading1..heading9 (3–11), bullet (12), ordered (13), code (14), quote (15), todo (17),
  table (31), table_cell (32) and **add_ons / Mermaid (40)**. Types 2–32 are the
  **Markdown-expressible set** (the Markdown-authoring spec § D2); each is a `NewBlock`
  kind — a heading carries a level 1–9, the three list kinds nest, code carries a language,
  a table takes an R×C grid — **except `table_cell` (32), which has no kind of its own**: a
  cell comes into existence **with its table** (Lark auto-provisions the grid from the
  table's property and the engine then fills each cell). Authored text is unstyled — with
  **one** exception, the **link anchor** (LD-619): a cell authored as a `TextSpan` sequence
  rather than a string carries `text_element_style.link.url`, which Lark was measured to accept
  and **store** on both write routes (`dev/ld517-in-cell-link/findings.md`, ruled by `D-110`).
  Every other run styling in a cell is not a field on a `TextSpan` and was not measured there.
  **Type 40 (LD-192) is the one whose payload is not text elements** — its content is a
  `record` JSON string inside `add_ons`, so `NewBlock.mermaid(source, theme=None)` takes
  already-compiled Mermaid source (compile one with `larkdocio.mermaid`). It is also the one
  that is **creatable but not editable in place**: no `add_ons` updater exists on the docx
  block-patch surface, so changing a diagram is **delete + re-create at the same index** and
  the `block_id` changes. That is why row 40's word could not flip on a doc edit alone — the
  column is pinned against `larkdocio.write.encode.CREATABLE_BLOCK_TYPES`, so it moved in the
  same commit as the encoder, which is the coupling this summary exists to make visible.
- **`editable` (0):** `none` — no row carries this state today, and that is the *point* of
  the state rather than a gap. **`editable` means editable-but-NOT-creatable**, and since
  LD-135 the **editable ≠ creatable** nuance (dogfood **F9**) is carried by the **merge**
  case *inside* type 31 rather than by any whole type: a **merged** table reads (as HTML)
  and its unmerged cells edit through a `TableLocator` anchor, while **no merge can be
  authored** — Markdown has no colspan/rowspan, so a ragged grid is refused
  (`merge-not-expressible`), never approximated. A cell covered by or anchoring a span is
  neither: it refuses `write-hostile-target` on an edit *and* cannot be created.
- **`creatable-out-of-band` (2):** `27` — image, created by
  `larkdocio.write.media.put_image_in_document` — and `23` — the 📎 file attachment, created by
  `larkdocio.write.media.put_file_in_document`. **One function per block type, and the pairing
  matters**: calling the image op for a file mints a **permanent, unpurgeable** media token
  bound to the wrong block type, and no open-API verb purges it. Neither is a `NewBlock` kind,
  because a body binary needs **bytes** and the Markdown compiler has none: the image op
  creates the empty type-27
  block, uploads the bytes **bound to that block id**, and binds them with a
  `replace_image` PATCH, in that order, taking the **read-back** as the verdict (the upload
  answering `code:0` is not a bind). The span is pinned against
  `larkdocio.write.media.OUT_OF_BAND_CREATABLE_BLOCK_TYPES` in both directions, so an op that
  starts creating another block type without moving its row reddens the suite. A Markdown
  `![](…)` through `compose()` is still refused — same reason, from the other side. The
  **file attachment** (`23`) takes the same route with one extra step nobody could guess:
  the create answers a **type-33 view wrapper**, so the op resolves the wrapper's child,
  confirms it reads back as a type-23 block *before* uploading, binds with `replace_file` on
  the child, and returns the **child's** id. It is a **different product from an inline
  sentence link** — a 📎 card in the body, not an anchor on a run — and the type-33 wrapper
  itself stays `not-creatable` (creating it directly is refused).
- **`not-creatable` (all the rest):** the write-hostile subset is
  `18, 26, 30, 43, 49, 50, 53` (bitable, iframe, sheet, board, source_synced /
  reference_synced, reference_base) — those hold no patchable text, so they refuse an
  **edit** as well (`WRITE_HOSTILE_NODE_TYPES`, which also carries image 27 for the same
  edit-side reason even though 27 is now creatable out of band). Everything else outside the
  creatable spans is simply outside this rung: boards, embedded surfaces, callouts, grids and
  colors are each a **future rung**, and inexpressible today rather than merely refused
  (`NewBlockKind` is closed; `NewBlock` carries no token, url or span field). Not counted
  here because the count would be an unmaintainable duplicate of the matrix.

**The endgame invariant (T3):** the `unregistered-warns` class is **EMPTY for every SDK-known type (1–53)** —
each is `rendered` | `placeholder` | `intentionally-skipped`. The warn path survives **only** for `999`/undefined
(the forward-compat sentinel) and genuinely-future Lark types. Both the `rendered`/`placeholder` set (against
`blocks.get_registry()`) **and** this empty-warn-class invariant are asserted by
`tests/test_blocks_md_matrix.py`, so the matrix cannot silently drift from the registry — nor drift back to a
bare "unhandled today" label for any 1–53 type.

## Notes on a few types

- **Underline (type 2)** always emits an HTML `<u>…</u>` wrapper — intentional, because
  Markdown has no native underline and the HTML round-trips in any CommonMark renderer that
  allows raw HTML.
- **Headings 7–9 (types 9–11)** exceed Markdown's H1–H6 range and emit 7–9 literal `#`; this
  preserves the source's heading depth even though most renderers won't style them as headings.
- **Tables with merged cells (type 31)** are the one case where the reader emits **HTML**
  (`<table>` with `rowspan`/`colspan`) instead of a pipe table — a Markdown pipe table cannot
  express merges. Cell content is HTML-escaped on that path.
- **Boards (type 43)** are the catch-all for visual diagrams: native flowcharts (21) and
  mindmaps (29) are delivered by Lark as boards and picked up here.
- **Documented-skips & the endgame invariant (T3):** after T3 **no SDK-known type (1–53) is a bare
  `unregistered-warns`** — each is `rendered`, `placeholder`, or `intentionally-skipped` with a stated
  reason. The skips fall in three buckets: **superseded** (diagram 21 / mindnote 29 arrive as Board 43),
  **re-serialized** (link_preview 48 arrives as iframe 26), and **feature-gated, no live payload** (20,
  28, 36–39, 41, 42, 51, 52 — uncreated in the zoo; 42/51 gated on the optional wiki page). **Task 35**
  arrives scope-redacted to `999 {}` today (no id to mark) so it stays a warn — a placeholder is
  **conditional on a future scope grant**. **999/undefined** is the sole remaining warn: the forward-compat
  sentinel for types Lark adds later. Speculative handlers are not built until a real payload appears
  (the read-completeness spec § Decision b/f).
- **Synced blocks (49/50):** the origin (49) is rendered in place (inline elements + its
  children); the reference (50) is a placeholder because cross-document resolution needs read
  access to the *source* document that this integration typically isn't granted.
- **Embedded data (18/30/53):** an embedded **Base** (bitable 18), **Sheet** (30), or a base
  switched to a **named view** (reference_base 53) each carries only an id (`token`; 53 also a
  `view_id`) — the records/cells/views live in a *separate* Base or Sheet document. Each emits a
  📊 traceable placeholder marker (LD-048) by default rather than dropping. **All three now have
  an opt-in deep read**, and the default is unchanged for all three (the placeholder,
  byte-identical, zero API calls): **Sheet (30)** with `deep_read_sheets` reads the referenced
  **tab** inline (LD-105), and **Base (18/53)** with `deep_read_bases` reads the
  referenced **table** inline through ONE shared bridge (LD-250). A failed
  deep-read degrades back to the placeholder on every path — a download never fails because an
  embed could not be read.
  **18 vs 53:** embedding a base yields a type-18 bitable; switching it to a named view converts
  it to a type-53 reference_base — distinct types a consumer hits interchangeably, so both
  markers name the relationship and both ride the same deep-read bridge (a *stale* embed token
  is a state, not a type). **Creatability, stated precisely because it is easy to get wrong:**
  the Write column is about **larkdocio** and stays `not-creatable` for both. **Lark's** own API
  will create a type-18 embed with `{"view_type":1}` — auto-provisioning a fresh doc-owned Base —
  but refuses `1770001` if you supply a token, and refuses a type-53 create outright (`1770029`).
- **Typed model + renderer (T2):** the reader was migrated from string concatenation to a
  **typed block/document model** (`src/larkdocio/model/`) serialized by ONE Markdown renderer.
  **Every** handler now constructs model nodes — the pilot families (divider 22, quote 15,
  headings 3–11; LD-024), then text/code/equation (LD-025), lists (LD-026), table (LD-027),
  callout/quote_container/grid (LD-028), media/file/diagram (LD-029), synced (LD-030), and
  finally **page (1) + the parser-core spine** (LD-031 — the LAST family). The parser spine
  now builds a **node tree**: `parse_docx_node` produces the typed node (dispatch + the
  missing/unknown-block empty `RawBlock` sentinel), and the renderer alone serializes that tree
  to Markdown via `render(node, depth)`. R-S5 (LD-038) deleted the transitional string-boundary
  delegate once every family carried child nodes, so `parse_docx_node` is the **sole** recursion
  primitive. The **recursion/indent contract** is now explicit (see `blocks/BLOCK_TYPES.md`
  § authoring guide); the list-item indent tab is owned by the renderer's list-item serializer
  (threaded via `depth`), not a string boundary. **Every** family — page, **the list family (12/13/17)**, the
  **recurse-at-0 containers heading (3–11) / callout (19) / quote_container (34)**, the **table
  family (31/32)** and the **own-depth recursers grid (24) / source_synced (49)** — carries real
  child NODES (R-S1 flipped the list carriage, R-S2 the recurse-at-0 group, R-S3 the table
  family, R-S4 grid + source_synced; the whole document object is now a node tree, output
  byte-identical throughout). The renderer carries an escape-literals policy option, **default OFF** (raw
  passthrough — today's behavior). The LD-024 **strangler shim** — which let a handler return a
  legacy Markdown string OR a node during the migration — had its string arm **removed in
  LD-032**; every handler now returns a `Node` only (`BlockHandler` is typed `Callable[..., Node]`).
- **Docx block anchors ARE mintable; docx `#share-` section anchors are not.** The two fragment
  grammars look alike and are different claims, so each is authored once and quoted verbatim here
  and in the shipped guide. **(1) The bare fragment** — `larkdocio.common.docx_block_url(doc_url,
  block_id)` builds `…/docx/<doc>#<block_id>` offline from a block id this surface already emits
  (`emit_block_ids` / `project_block_ids`), authored at
  `larkdocio.common.url.DOCX_BLOCK_ANCHOR_MEASUREMENT`, which carries the edge of its own evidence:
  A docx block link (`…/docx/<doc>#<block_id>`) IS mintable, offline: `docx_block_url(doc_url, block_id)` builds one from the document's own URL and a block id the reader already emits, and makes zero API calls. Here is the edge of the evidence, so the claim is never read wider than what was measured. The bare fragment was clicked on 2026-08-10 in the Lark WEB client, on one tenant, against all six block kinds tried: heading1, heading2, paragraph, table, bullet and code. Every one of them anchors — a heading, paragraph or bullet target is jumped to, while a table or code target is moved to with a momentary highlight, which is how those blocks show a selection. The `?blockId=<block_id>` query form was clicked in the same sitting and does nothing at all. UNMEASURED, and therefore neither refuted nor supported: the mobile client, the desktop app client, wiki-wrapped documents (`…/wiki/<node>`, which this function refuses rather than guess at), and any other tenant. Whether a link scrolls is a rendering behavior of the Lark client, so no API call can widen this measurement — only another click can.
- **(3) The named-edition link** — `larkdocio.common.docx_edition_url(doc_url, version_token)`
  builds `…/docx/<doc>?edition_id=<version token>` offline, under the same fencing as (1),
  and carries a label clicked on exactly one client on one tenant, authored at
  `larkdocio.common.url.DOCX_EDITION_LINK_CLICK_MEASUREMENT`:
  A docx named-edition link (`…/docx/<doc>?edition_id=<version token>`) is mintable offline — `docx_edition_url(doc_url, version_token)` builds one from the document's own URL and a version token, and makes zero API calls — and it ships click-verified — the `?edition_id=` grammar was clicked on 2026-08-11 in the Lark WEB client, on one tenant, and it opened the named version. Here is the edge of the evidence, so the claim is never read wider than what was measured. The click was made against a harness-created two-paragraph document whose two states were proven to differ AT THE API LEVEL first — a read pinned at the version's recorded revision returned the first paragraph only, while a head read taken in the same sitting returned both — so a browser showing one state could not be an accident of the fixture. MEASURED: the QUERY half, by that click; and the PATH half, `https://<tenant host>/docx/<doc token>`, which is the document's URL as Lark itself reports it (the drive metas/batch_query verb asked `with_url: true`, 2026-08-11), and it is character-for-character the grammar `docx_block_url` already mints; the version token is Lark's own, returned by the versions family. Separately, and unchanged by the click: no API route resolves an edition token to CONTENT — the versions family answers no url of any kind, and an edition token resolves to nothing — so keep recording the (name, token, revision) triple at creation time, because that pairing is what a pinned historical read actually runs on.
- **(2) The `#share-` section link** (the "copy link to this heading" the Lark web client mints) can
  be *parsed* by `larkdocio.common.url.parse_deep_link` into a `DocAnchor(doc_token, share_token)`
  and its opaque `share_token` carried unaltered, but it can be neither minted nor fetched — and the
  near-miss spelling of one is hazardous. Authored at
  `larkdocio.common.url.DOCX_SECTION_ANCHOR_UI_ONLY`: A docx section link (`…/docx/<doc>#share-<token>`) is UI-only: this library cannot mint one and cannot fetch one. The fragment is a share token the Lark web client mints when a person copies a section link; it is NOT a block id (an exhaustive check of a real document's every block found no match, and the block-get endpoint returns not-found for the share token while returning the block for a real id), and no docx share or permalink endpoint exists to turn it into anything the API will accept. This is not a permissions problem: the data does not exist in the API at all, so no grant would change either answer. That verdict is about the `share-` grammar and nothing wider: the OTHER docx fragment grammar — a bare `…/docx/<doc>#<block_id>` — IS mintable, and is a separate measured claim (see `docx_block_url`). Do not try to bridge the two. The obvious guess, `…/docx/<doc>#share-<block_id>`, navigates nowhere and shows a toast reading "The selection content has been deleted" about content that is perfectly intact — observed on every block kind tried, and the same lie-class as the sheets cell-link toast: a reader who sees it will file a data-loss bug against your document or against this library. To point at a passage in band, emit the block ids with `emit_block_ids` and mint the bare-fragment link with `docx_block_url` — a share URL is not available.
