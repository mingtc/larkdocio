# SHEETS.md — larkdocio Sheets capability matrix

**The single source of truth for what larkdocio's Sheets surface supports** — the
BLOCKS.md twin for spreadsheets. Where [`/BLOCKS.md`](BLOCKS.md) pins how the docx reader
treats every block type, this file pins how the Sheets surface reads (and, once built,
writes) every cell type, structural feature, and API operation.

> **Citations into `dev/`, `progress/` and `requirements/`** in this file are provenance
> notes **in the dev repo**, pointing into the maintainers' private records, which the public
> repository does not carry. Read each as provenance for the fact stated beside it.
> A recorded API response is cited at its `tests/captures/…` copy where the repository carries
> one; a recording cited under `dev/` is a maintainers' record the repository does not carry.

**Scopes are not authored here.** Where a row names a Lark scope it is quoting the single
source, `larkdocio.permissions` — the per-operation permission registry, whose maintainer-side
projection is [`/PERMISSIONS.md`](PERMISSIONS.md). Add an operation and its scope row belongs
there, not in this file.

This file is **current-state + spike-characterized**. Two disciplines keep it honest:

1. **Verified evidence only.** Every row is sourced from **shipped L1 code/tests**
   (`src/larkdocio/sheets/`), the **LD-100 read spike** (`dev/sheets-spike/report.md` +
   `captures/`), or the **LD-107 write spike** (`dev/sheets-write-spike/report.md` +
   `captures/`). Nothing is speculated — anything not observed is an honest **`uncaptured`**,
   never a guessed status.
2. **Drift-guarded.** [`tests/test_sheets_md_matrix.py`](tests/test_sheets_md_matrix.py)
   cross-checks this file against the code that exists **today** (the BLOCKS.md
   registry↔matrix guard's shape): every renderer dispatch branch has a cell-type row and
   vice-versa; every shipped read op has an operations row and vice-versa; every
   `shipped-L1` row names real, importable code; every status is a recognised slug; every
   row carries evidence. If a row disagrees with the code, the row is the bug.

> **Read vs write, L1 vs L2.** The **read L1** surface is **shipped** (LD-101..106): a
> standalone Sheets values→Markdown reader + an opt-in docx embedded-sheet deep-read. The
> **value-write** surface shipped with **the Sheets value-write spec** (LD-109: the throttled, typed
> `SheetsWriteClient` — values put/batch/append/prepend, always `Start:End`, WRITE creds only),
> and the **plan-gated, findings-agnostic value-write apply engine** (LD-111:
> `src/larkdocio/sheets/write_apply.py` — non-forgeable `Plan` → mandatory dry-run → apply, with
> the `revision` compare-and-swap `STALE_SHEET` staleness guard, D5). The **leak-proof
> self-provision harness** shipped with **LD-112** (`tests/sheets_write_harness.py` — the
> disposable create→populate→mutate→verify→delete-in-`finally` lifecycle + a persisted ledger +
> a zero-orphan close-out, the Sheets twin of the docx W0 harness). **THE SHEETS VALUE-WRITE GATE — the
> binding `live_write` values-leg round-trip — shipped with LD-113**
> (`tests/test_live_sheets_write_gate.py`; the pure used-range differ is
> `tests/sheets_values_diff.py`): on a self-provisioned disposable, a plan-gated value write →
> **used-range values-leg surgical diff** (only the target range changed, every other cell
> byte-identical) → **byte-identical restore** → delete → zero-orphan close-out, joining the ONE
> `pytest -m live_write` ring so all families (docx W0..W3 + this sheets family) pass together.
> **The Sheets value-write tranche is closed.** **L2 style/format fidelity shipped with the Sheets read-fidelity spec**
> (LD-114 the xlsx-export reader + typed cell model; LD-116/LD-118 the two-leg fidelity differ +
> THE L2 GATE), and the **rich + structural write surface shipped with the Sheets rich/structural-write spec** — rich-cell
> encoders (LD-119), the dropdown-rule family (LD-120), structural dimension writes (LD-121),
> merge/unmerge + tab writes (LD-122), and the destructive-safe apply consolidation (LD-123).
> **⛳ THE ARC'S FINAL GATE — LD-124 (`tests/test_live_sheets_final_gate.py`) — closes the Sheets
> write beast:** one `pytest -m live_write` run round-trips **all four rich/structural write
> kinds** on a self-provisioned disposable, EACH under the **full two-leg differ** (values leg +
> style/format export leg AUTO-ON + merge leg — D9), with the **destructive-safe removed payload**
> asserted from a live delete (D5), byte-identical restore, and a zero-orphan close-out — joining
> the SINGLE ring so **every family (docx W0..W3 + sheets value + sheets style-leg + rich/
> structural) passes together.** The Sheets **read + write surface is now fully shipped.** Every
> value-write / read-fidelity / rich-structural story carried a SHEETS.md-row-update AC, so this file is the running registry
> those tranches kept truthful.

**Cell-type write-support** (the CELL-TYPE matrix's `Write support` column): `shipped-rich-structural`
(the rich-cell **write encoder** ships in the gated engine — `larkdocio.sheets.rich_encode` +
`write_apply.RichCellWriteRequest`, LD-119; the live round-trip is the QA gate) · `proven-in-spike`
(a write spike wrote this exact cell type and read it back, not yet built into `src/` — LD-107
for the rich-cell family, LD-435 for the in-cell image) ·
`planned` (slated for a write spec) · `parked` (not a write target) · `uncaptured` (write not
characterized).

**Render branch** (the CELL-TYPE matrix's machine column): the dispatch branch
[`render_cell`](src/larkdocio/sheets/render.py) actually takes for that cell's L1 (default
`FormattedValue`) wire shape — `none` · `bool` · `number` · `string` · `segments` ·
`segment:text` · `segment:url` · `segment:multipleValue` · `segment:mention:user` ·
`segment:mention:doc` · `segment:embed-image`. The drift guard pins this column bidirectionally against the renderer's
source, so a new/removed branch reddens the suite.

**Multi-select read/write asymmetry (load-bearing).** A multi-select cell **reads back** as a
**comma-joined string** under **every** render mode (LD-107 Q3, and the maintainer's own scratch-sheet
2+ capture 2026-07-27 — confirmed twice); the `{"type":"multipleValue"}` object is the **write**
encoding only. **Since LD-117 D5b `render_cell` normalizes BOTH shapes to the same ordered `", "`
set** (object → join; comma-joined string `"Red,Green"` → `"Red, Green"`), the ONE deliberate
default-MD change. Because a bare comma-joined read string is indistinguishable at the value layer
from a formatted number (`"$1,234.56"`, `"3,14"`), the string normalizer applies a **digit-flank
guard**: a comma flanked by digits on both sides marks a numeric grouping and is left untouched —
so currency/decimal/thousands strings are preserved (only a genuine, comma-free-label set is

## Hard limits on the shipped ops

The ceilings a consumer meets at scale, and that larkdocio's own gates ride. They were absent
from this file until LD-152 — an op documented as shipped without its ceiling reads as
unbounded, and the first symptom of a missing ceiling is a rejected call at the size where it
matters. Sourced from the 2026-07-28 API-coverage audit (primary-source Lark docs) plus the
LD-100 read spike; nothing here is inferred from a failure we saw.

| Limit | Value | Applies to | Evidence |
|-------|-------|------------|----------|
| values per write call | **≤5000 rows × 100 columns** | `SheetsWriteClient.put_values` / `batch_update_values` / `append_values` / `prepend_values` (and every `ValueWriteRequest` / `RichCellWriteRequest` / `FormulaWriteRequest` through them) | `dev/sheets-api-coverage-2026-07-28.md` § Corrections |
| characters per cell | **≤50,000** — with a **documented disagreement**: the LD-100 spike's own FAQ capture says **45,000**, so treat 45,000 as the safe floor until one is probed | any value write — `SheetsWriteClient.put_values` and the rich/formula encoders that ride it | `dev/sheets-api-coverage-2026-07-28.md` § Corrections · `dev/sheets-spike/report.md` § Q5 (worksheet ceilings) |
| response size per read | **≤10 MB** | `SheetsReadClient.get_values` / `batch_get_values` / `read_used_range` and `SheetsWriteClient.read_values` — page by row bands within the used range for a big tab | `dev/sheets-spike/report.md` § Q5 (limit posture) |
| rows/columns per dimension op | **≤5000** | `SheetsWriteClient.insert_dimension_range` / `delete_dimension_range` / `append_dimension` (`InsertRowsAt` / `DeleteRows` / `AppendDimension` …) | `dev/sheets-api-coverage-2026-07-28.md` § Corrections |
| spreadsheet create | **20/min tier** | `SheetsWriteClient.create_spreadsheet` — and through it the `sheets_write_harness` disposable provisioning: **a gate-scaling ceiling**, because the disposable-per-test pattern rides this tier, so adding live-write gates (or a create-per-run consumer loop) costs against it | `dev/sheets-api-coverage-2026-07-28.md` § Corrections |
| cells per spreadsheet | **5M** (plus ≤13,000 columns, ≤300 sheets) | any write that grows a tab (`append_dimension`, `insert_dimension_range`, `AddTab`) | `dev/sheets-spike/report.md` § Q5 (worksheet ceilings) |

**None of these is enforced client-side today** — larkdocio does not pre-refuse an oversized
write, so an over-ceiling call is answered by Lark and surfaces as a typed `LarkAPIError`
through the ordinary disposition boundary. Documented here so the ceiling is discoverable
before it is hit; a plan-time refusal for the two that are cheaply checkable (the values arity
and the dimension span) is a backlog item, not a shipped behavior.

## Notes / asymmetries / caveats

- **WHO MAY USE A SPREADSHEET is a DRIVE-surface question, and it is now answerable (LD-456).** Nothing in this matrix grants access — the Sheets surface reads and writes a workbook's *content* — but the neighbouring `drive-access-write` surface addresses a spreadsheet's member family on the WRITE pair: `DriveAccessWriteClient.grant_access(spreadsheet_token, email=..., perm=..., obj_type='sheets')`, with `update_access` / `revoke_access` / `list_members` alongside it. **Measured live** on a harness-created disposable workbook — an empty member list at birth, a grant that stored, a revoke that left the list empty, each judged by an independent read-back — and, as that gate's control, the same token addressed as a `docx` still answers Lark's `1063001`. It is noted here because a workbook the app *created* is one nobody else can open until a human is put on it, and this matrix is where a reader looks for the spreadsheet's own truths. See `DRIVE.md` for the surface's evidence and its refusals.
- **The multi-select asymmetry** (read = comma-joined string under all modes; write = the
  `multipleValue` object) is confirmed **twice** — LD-107 Q3 and the maintainer's own scratch-sheet 2+
  capture (progress.md 2026-07-27). A write differ normalizes both sides to an ordered label set;
  commas are **forbidden inside option labels**. **SHIPPED (LD-119):** the write encoder
  (`larkdocio.sheets.rich_encode.encode_multi_select`) normalizes labels to the ordered set and
  **refuses a comma-in-label** (`MultiSelectLabelError`, typed); the differ normalizer
  (`normalize_multi_select`) **reuses** the LD-115 `MultiSelect.from_wire` (no fork) to unify both
  wire forms — the write object and the comma-joined read string — to the same ordered tuple.
- **Formulas: the object form evaluates, a `"="` string never does** (LD-149, dogfood round-2
  **T23**; probed live on a self-provisioned disposable 2026-07-28, deleted, zero orphans). Round 2
  wrote `"=SUM(B3:B8)"` as an ordinary value and read back the **literal string, unevaluated —
  silently**. The characterized reality, in five parts:
  1. **The documented object form `{"type":"formula","text":"=SUM(...)"}` written through the same
     values `PUT` DOES evaluate.** Read-back: `Formula` → the **expression** `"=SUM(B3:B8)"`;
     `UnformattedValue`/`FormattedValue` → the **computed value** `21`; `ToString` → the expression
     with the leading `=` **stripped** (`"SUM(B3:B8)"`). **SHIPPED as
     `write_apply.FormulaWriteRequest`** through the gated engine.
  2. **A plain `"=…"` string can NEVER evaluate, and there is NO `valueInputOption` on this API.**
     `?valueInputOption=USER_ENTERED`, `?valueInputOption=RAW`, and a body-level
     `valueInputOption` are each answered `code 0 / "success"` and have **zero effect** — the
     string stays inert (probed all three ways). So a `=`-prefixed **plain** value earns a **LOUD
     dry-run note** (`plan.entries[i].preview_note`, text pinned as
     `larkdocio.sheets.formula.INERT_STRING_NOTE`) rather than being silently converted; nothing
     about the existing value path changes.
  3. **`Formula` mode alone CANNOT tell inert `=`-text from a real formula** — both read back the
     identical string. The ONE discriminator is the **computed leg**: a cell evaluated iff its
     `UnformattedValue` read-back **differs** from its stored expression. Apply therefore re-reads
     both legs after the write and records `evaluated` in the apply-log's `formula` record
     (`ApplyLog.formula_not_evaluated` is the one-line consumer assertion).
  4. **An invalid formula is ACCEPTED, not refused.** `"=SUM("` comes back `code 0` and is stored
     **inert** — there is no API error to catch, which is precisely why (3) is the detection. A
     **bad function name** (`"=NOTAFUNC(B3)"`) by contrast *does* become a live formula whose
     computed value is the error sentinel `"#NAME?"` (flagged `error_value`), as does a bad
     reference (`"#REF!"`). A formula over empty cells evaluates to `0`.
  5. **The precondition compares the EXPRESSION, not the computed value** (maintainer-adopted): editing one
     operand moved the computed value `21`→`120` with the expression untouched, so comparing the
     computed value would refuse writes nobody made. **Two inversions worth knowing:** a formula
     **reference** addresses a tab by its **TITLE** (`=SUM(Other!A1:A2)` → `30`; Lark normalizes it
     to `=SUM('Other'!A1:A2)`) while a `sheet_id` reference evaluates `#REF!` — the exact opposite
     of the A1 write-range rule below; and a **plain value write over a formula cell silently
     replaces the formula with a static value** (the value path sees only the computed value), so
     use a `FormulaWriteRequest` when you mean to rewrite the formula. Writing a formula into a
     **merge anchor** works; a merge-**covered** cell refuses `merged-cell-target` as for any value.
- **The plan/dry-run/apply-log DISCLOSURE vocabulary — the complete list** (LD-150; the seat
  dogfood's nine holes, F21/F9/F8/F20/F24/F16/F22/F23/F12). This is the canonical naming; the
  consumer guide's recipes quote it verbatim.

  | Kind | Name | What it says |
  |------|------|--------------|
  | refusal reason | **`shape-mismatch`** | the proposed values' arity ≠ the target range's shape. **Pre-I/O**, zero reads; the detail names both shapes + both repairs (resize the matrix, or narrow the target). Refused rather than resolved because the uncovered cells' fate is undescribable — the observed failure was silently blanking them. |
  | refusal reason | **`malformed-range`** | the range is not an addressable rectangle (reversed `C3:A1`, sub-1, past the 100-column notation ceiling). Caught **pre-I/O** by `WriteRange.validate()`, and mapped from Lark's `90202 validate RangeVal fail`. Replaces the mislabelled `tab-vanished` for this case; **`tab-vanished` still means staleness**. |
  | note kind | **`overwrites-live-formula`** | this write/clear destroys N live formulas; each cell's `ref`, `expression` and `computed_value` enumerated. Costs one `Formula`-mode read. An **inert** `=`-string is not reported. |
  | note kind | **`no-merge-at-range`** | this unmerge intersects none of the merges the plan was **given** (`dry_run(..., merges=…)`), so it dissolves **nothing**. Not a refusal, zero extra calls. |
  | note kind | **`out-of-bounds-dimension`** | this delete's span runs past the tab's row/column count (`span`, `count`, `overshoot`, `wholly_out_of_bounds`). Built from the geometry the preview already read. |
  | note kind | **`multiple`** | the envelope an entry earning **several** disclosures carries (`notes: [...]`), so no warning displaces another. |
  | accessor | **`PlanEntry.preview_notes`** / **`ApplyLogEntry.preview_notes`** | every disclosure on the entry as a tuple, flattening the single-note and `multiple` shapes to one shape. |
  | accessor | **`ApplyLogEntry.preview_note`** | the plan entry's disclosure, **carried** onto the log entry (every disposition, stamped at the one `apply()` seam). |
  | accessor | **`ApplyLog.inert_formula_strings`** | every entry that **landed** having stored a `=`-prefixed plain string. With `formula_not_evaluated`, the two-part CI assertion the guide ships. |
  | typed error | **`A1RangeError`** (`write_range`) | an A1 *form* fault, with a valid-form example. A `LarkConfigError` subclass. |

  | disclosure field | **`removed["values_trim"]`** | `{axis, declared, used}` for a delete's trimmed removed payload (F12). |
  | docx parity | **`PlanEntry.precondition_text`** on a sub-span | the id-anchored sub-span plan now shows its compare-and-swap basis like edit/insert/delete (F16). Disclosure only — the sub-span apply path re-validates the **span**, and never consulted this field. |

  Zero-drift discipline: every one of these is **additive**, and each optional wire key
  (`preview_note`, `values_trim`) appears **only when earned**, so a plan/log that earns no new
  disclosure serializes byte-identically to pre-LD-150. The whole vocabulary is pinned by
  `tests/test_sheets_plan_disclosure_completion.py` (with a bite test), so a future change
  cannot drop one silently — which was F8's whole lesson.
- **The export-only fidelity ceiling** (LD-107 Q2, the L2 crux): a cell's **style**
  (bold/fill/font) and its **number-format pattern** are **NOT readable** through the values API,
  `metainfo`, or any v3 surface. `FormattedValue` bakes a number format into a *display string*
  but never exposes the pattern. The **only** full-fidelity style/format read is the drive
  **`export_tasks` → xlsx** path (`xl/styles.xml`). So an L2 fidelity differ has two legs — a
  cheap live values leg and a heavier export-based style/format leg.
- **Structural index conventions differ** (LD-107 Q4): `insert_dimension_range` is **0-indexed,
  half-open `[start,end)`**; `dimension_range` DELETE is **1-indexed, inclusive `[start,end]`**;
  v3 `merges` are **0-indexed, END-inclusive**. Never assume parity — trust the reply's
  `addCount`/`delCount` and re-read geometry after any structural write. **Shipped (LD-121):**
  the asymmetry is now encoded **structurally** — the caller-facing gated request objects
  (`write_apply.InsertRowsAt`/`InsertColsAt` carry a `before_*` position; `DeleteRows`/`DeleteCols`
  a 1-indexed inclusive `first`/`last`) convert to each endpoint's native convention internally, so
  a wrong-convention span is not expressible (D3); apply trusts the reply count + mandatorily
  re-reads geometry (`SheetsWriteClient.read_sheet_geometry`). **The caller-facing positions are
  1-based against displayed position** —
  `before_col` is **1-based against displayed column position** and `before_row` is
  **1-based against displayed row position** — which for an *insert* is a
  DIFFERENT base from the wire span printed beside it, so the plan's `semantic` line names both and
  its `convention` line describes only `start_index`/`end_index` (LD-461: a consumer who read the
  wire convention as the parameter's own inserted one column early and shifted live data).
- **A write range addresses a tab by its `sheet_id`, never its `title`** — and a wrong-kind id is
  now REFUSED TRUTHFULLY (LD-131, dogfood F4/F5). The read side hands back a `SheetTab` object and
  hides ids, so nothing in the read flow teaches you that ids are the write-side currency; Lark
  answers a title-shaped prefix with `90215 not found sheetId`. At **plan** time the engine now
  classifies that failure: if `query_tabs` proves the prefix is not one of the spreadsheet's tabs the
  entry refuses **`UNKNOWN_TAB`** with a **did-you-mean** listing the real `(sheet_id, title)` pairs
  (titles `repr`-quoted so a title containing a `!` cannot be misread as the A1 separator), and the
  detail says outright when the string is a real tab's *title*. **`TAB_VANISHED` is RESERVED** for a
  range that WAS readable at plan time and is unreadable at apply re-validation. The extra
  `query_tabs` read happens **only** on the failure path — the happy path is unchanged. Accepting
  title-or-id in a range is deliberately NOT done here (a feature, deferred); the refusal just tells
  you the right id.
- **Merge geometry** lives **only** in the v3 tab-query `merges` array; a values read alone cannot
  reconstruct it (every covered cell reads `null`, indistinguishable from a genuinely empty cell),
  so the merge join is the authority.
- **The typed cell model is additive (D3, LD-115).** `larkdocio.sheets.cell_model.TypedCell` is a
  richer parallel surface — raw+display **dual** value, `segmentStyle` runs + hyperlink/mention/
  multi-select **structure**, the export-only numFmt/fill/bold/italic **fidelity** (populated from the
  LD-114 export reader, `None` when no export), and **merge membership** — that the write-gate differ
  (S3) and the MD gains (S4) consume. It **captures what render drops** (a run's `foreColor`/`fontSize`,
  a cell's fill ARGB) for the differ, but adds **no** MD render change on its own: the shipped
  `render_cell`/table path is byte-identical (the model itself is never imported by the render path).
- **`90202` bare-single-cell caveat:** the range-bearing v2 endpoints (`values` PUT/GET, `style`
  PUT) reject a bare cell (`{sid}!A1`) with `90202 wrong range` — always emit `Start:End`
  (`{sid}!A1:A1`). The array-taking `styles_batch_update` is immune.
- **Determinism:** two same-run reads of an unedited sheet are **byte-identical** (`revision`
  stable, `34→34`); every write bumps `revision` by exactly +1 (the compare-and-swap staleness
  anchor). Reads never bump it.
- **Verifying a write: compare values, not their string forms (LD-190 / round-3 F19).**
  A SHEET'S NUMERIC READ-BACK IS NORMALIZED, so verifying a write by comparing STRING FORMS reports a phantom difference. Measured live: every whole-valued float comes back as an int — 18.0 reads back as 18, 0.0 as 0, -3.0 as -3, 1e6 as 1000000, and 2.5*4 as 10 — while a non-whole float is returned untouched (22.5 stays 22.5) and a string stays a string ('18.0' stays the text '18.0'). An empty cell reads back as null, and a trailing empty cell may not be returned at all. So str(written) == str(read_back), json.dumps of the two matrices, and a diff of two rendered Markdown tables all report a change on every whole number in the sheet, and none of those changes happened. Compare values, not their string forms: larkdocio.sheets.values_equivalent(written, read_back) compares numbers numerically across int/float, treats an empty cell and an absent trailing cell as the same emptiness, and keeps every REAL difference visible — a text '18.0' is not the number 18, a bool is not 1, and 18.01 is not 18. It is a typed comparison and NOT a tolerance, deliberately: the normalization changes a value's type and never its magnitude, so a fuzz factor would buy nothing and would hide the 18.0-to-18.01 drift you are checking for. larkdocio.sheets.value_differences(written, read_back, origin='A1') returns the same answer cell by cell, each difference carrying its A1 ref. Evidence: tests/captures/sheets-merge-variant-probe/captures/02-numeric-read-back.json in the source repository.
  The comparator is `larkdocio.sheets.values_equivalent` (with
  `value_differences` for the per-cell answer) — the sheets parity of the docx side's
  compose-equivalence recipe, authored once at
  `larkdocio.sheets.verify.NUMERIC_READ_BACK_NORMALIZED` and quoted here and in the
  shipped guide.
- **Native vs pasted authority:** the LD-100 fixtures are the maintainer's **hand-recreated native**
  cells (col D + hand-adds B20–B24); a paste from xlsx drifts (drops formulas, carries foreign
  number formats and `rgb()` colors), so the native column is the fidelity target and the pasted
  column is a documented drift reference.
- **Deep links — tab links mint, cell links do not.** `larkdocio.sheets.tab_url(sheet_url,
  sheet_id)` is a pure, offline function that builds the one click-proven spreadsheet deep link
  (`<tenant-host>/sheets/<spreadsheet_token>?sheet=<sheet_id>`); the tenant host is an input read
  off the sheet's own URL, never the API domain. A cell/range link is a different story, stated
  once at `larkdocio.common.url.SHEETS_CELL_LINK_UI_ONLY` and quoted verbatim here and in the
  shipped guide: A sheets cell or range link is UI-only, and guessing one is hazardous. The `rangeId` in `…?sheet=<id>&rangeId=<id>_<opaque>&rangeVer=<n>` is opaque and versioned — a stored server-side object, not a computed address — and no endpoint in the Sheets surface mints, lists or resolves one. The obvious workaround makes it worse: a guessed `range=<A1>` URL half-works. It lands on the right tab and then shows a toast reading "The cell was deleted" about cells that are perfectly intact — identically for any coordinate, stably across refreshes. Do not build such a URL: a reader who sees that toast will file a data-loss bug against your sheet or against this library. This is not a permissions problem: the data does not exist in the API at all, so no grant would change either answer. Tab-level links ARE mintable — see `larkdocio.sheets.tab_url` — but cell-level ones are not. WHAT THIS IS AND IS NOT ABOUT: it is about a URL that POINTS AT a cell, and it is not about putting a link INSIDE one. Writing a cell whose value is a labeled clickable link SHIPS and works — `RichCellWriteRequest.hyperlink(range, link, text=…)`, worked through in the guide's section `Recipe: write a hyperlink and a styled run into a cell`. This paragraph is easy to misread as a verdict on that question, so the two are separated here rather than left adjacent.
