# BASE.md — larkdocio Base (bitable) capability matrix

**The single source of truth for what larkdocio's Base surface supports** — the fourth
living matrix, alongside [`/BLOCKS.md`](BLOCKS.md) (docx blocks), [`/SHEETS.md`](SHEETS.md)
(the Sheets surface) and [`/PERMISSIONS.md`](PERMISSIONS.md) (which Lark scopes each
operation needs).

> **Citations into `dev/`, `docs/`, `progress/` and `requirements/`** in this file are provenance
> notes **in the dev repo**, pointing into the maintainers' private records, which the public
> repository does not carry. Read each as provenance for the fact stated beside it.
> Recorded API responses are cited at their
> `tests/captures/…` copies, which the repository does carry.

**Scopes are not authored here.** Where a row names a Lark scope it is quoting the single
source, `larkdocio.permissions`, whose maintainer-side projection is
[`/PERMISSIONS.md`](PERMISSIONS.md). Add an operation and its scope row belongs there.

Two disciplines keep this file honest — the `SHEETS.md` standard, unchanged:

1. **Verified evidence only.** Every row is sourced from **shipped code/tests**
   (`src/larkdocio/base/`), the **UI-parity matrix**
   (`dev/base-study/ui-parity-matrix-2026-08-03.md`,
   including its `## Seat addendum`), the **P0 addendum**
   (`dev/base-study/p0-addendum-2026-08-03.md`)
   or the **opener** (`dev/base-study-2026-08-03.md`).
   Nothing is speculated — anything not observed is an honest **`uncaptured`**, never a
   guessed status.
2. **Drift-guarded.** [`tests/test_base_md_matrix.py`](tests/test_base_md_matrix.py)
   cross-checks this file against the code that exists **today**, bidirectionally: every
   `(type, ui_type)` the renderer registry dispatches on has a field row and vice-versa;
   every status is a recognised slug; every `supported` / `opaque` row names real,
   importable code; every row carries evidence. If a row disagrees with the code, the
   row is the bug.

> anchor is reported `dropped` rather than `applied`.

## Status vocabulary

One small, explicit slug set (the `BLOCKS.md` / `SHEETS.md` precedent). `uncaptured` is
the honest-unknown slug.

| Status | Meaning |
|--------|---------|
| **supported** | Built and tested in the shipped Base code (`src/larkdocio/base/`). Its code anchor resolves to real code — the drift guard enforces this. |
| **opaque** | **Captured, and what was captured is "there is nothing to read."** The field's *schema* is readable; its *values* are returned by **no** API read route. Not `uncaptured` — the absence is the finding. The renderer emits a visible absent-with-reason marker, never a blank. |
| **uncaptured** | Not observed. An honest unknown — never a guessed status. |
| **refused-by-server** | Lark's own API refuses the operation, server-declared (an enum, a typed error code). |
| **refused-by-policy** | larkdocio refuses it by its own doctrine (e.g. PII: an incidental email or avatar URL never reaches Markdown). |
| **will-not-support** | A **product ruling**. It survives the API gaining the capability — reopening needs a maintainer decision, not an API change. |
| **deferred** | **Captured, understood, and deliberately not built in L1** — a declared Non-Goal rather than a refusal by anyone. The API does not stand in the way; the scope decision does, and reopening it is a scope call. Distinct from `uncaptured` (nothing was observed) and from `refused-by-*` (something refuses). |

## Field matrix — the maintainer's picker names first

**The primary key is the UI name a consumer sees in their own field picker**; the API
identity `(type, ui_type)` is second (parity § 7 build-shape delta). Grouped exactly as
the picker groups them: **Basic / Business / Advanced**.

**28 UI types → 27 `(type, ui_type)` pairs** — Button has **no *authoring* identity** (it is
absent from both server enums, so it cannot be created) and no renderer is registered for it,
register row 4's maintainer ruling standing
— **→ 26 value renderers + the Stage opaque marker.**
It *does* have a **read** identity, `3001` / `Button`, which the offline evidence did not show
and THE L1 GATE found on a real Base: documented, deliberately unregistered, **register row
13.**

`Read status` is the *value* read (schema read is universal). `Render` is the shipped L1
Markdown. `Code anchor` names the dispatch entry in the read registry.

**`Write` is the other direction, and it is a different object for several types.** The column
carries the status, the **wire shape a write must send**, the encoder that builds it
(`larkdocio.base.write_cells`), and — the part that makes the row checkable — **the capture file
that shape was taken from**. Nothing here is derived from the read shape: a *predicted* wire key
answers `code:0` and stores nothing, so a shape without a capture is a guess with a docstring.
**19 of the 27 pairs are writable**; the other **8** are computed or opaque and are refused
**locally, before any call**, from the single set `larkdocio.base.write_vocabulary.NON_WRITABLE_PAIRS`.
The action-launcher type gets **no encoder and no bespoke refusal** — the generic
unregistered-pair refusal covers it, and a bespoke branch would be this library re-opening a maintainer
ruling that an API fact explicitly does not reopen (register rows 4 and 13).

## Client & operations

Every Lark call a shipped Base client makes, one row per op, in **two registries**: the read
client's ops and the write client's. **`mutates` is declared explicitly on each descriptor and
is never derived from the HTTP verb** — three Base reads are `POST`s and three record writes
are `POST`s too, so a verb-derived flag would be wrong in both directions at once. The `Verb`,
`Endpoint` and `mutates` columns are cross-checked against the code by
[`tests/test_base_md_matrix.py`](tests/test_base_md_matrix.py): the first two against the
pinned SDK request class's own `uri` / `http_method`, the third against the registry.

**Two registries, not one table with a flag column — and that is the design.** The read
registry ships `read_only()`, a helper three landed test files assert is `True` (two of them
live gates) and which the capability registry repeats to consumers in shipped text. Appending a
mutating descriptor to it would flip the helper and turn a true statement false while the read
surface had not changed at all. So the write descriptors live in their own ordered table with
their own accessor (`all_mutate()`), and *"is this op set read-only?"* stays a question each
registry answers about **itself**.

**Scopes are not listed here** — a scope requirement is authored in `larkdocio.permissions`
and projected into [`/PERMISSIONS.md`](PERMISSIONS.md). All six read families resolve to the
same read-mode row there; all six write families resolve to one write-mode row, on the **write**
credential pair.

**Transport:** SDK-typed throughout (the Base read spec § D2), with **no raw-HTTP fallback**, because no
SDK gap was hit. **Pace:** every call passes one shared limiter at the spacing the three
probe packs sustained — 483 live calls at ≥1.2 s with no limit met. Rate limits are
documented from that evidence and deliberately never probed.

### Schema writes — `larkdocio.base.schema_client.BaseSchemaClient`

**A THIRD registry, and an aggregator rather than a fourth flat tuple.** A schema write is not
one family but three — apps and tables, fields (both shipped), and views (a later rung) — so each
family ships as its **own** descriptor module and registers by adding one line to
`larkdocio.base.schema_ops.FAMILY_MODULES`. The flattened table below is those families in
registration order; `all_mutate()` answers about it, and the read registry's `read_only()` keeps
answering `true` about **itself**, because no mutating descriptor was ever appended to it.

**FIFTEEN structural ops, and FOUR of them delete — plus ONE whole-object delete that is not a
structural op at all** (`delete_base`, documented in its own table below the fifteen: it removes
the Base rather than something inside it, so it has no descriptor, no preview and no consent
token). Six are the non-destructive app-and-table
set, three are the field-authoring set, three are the **view lifecycle** — whose delete is
`DELETE …/views/{v}`, a verb whose blast radius is a view and which the server itself floors at
one view per table (`1254023 LastViewDeleteForbidden`) — and three are the **destructive family**:
`DELETE …/fields/{f}`, `DELETE …/tables/{t}` and `POST …/tables/batch_delete`, **the only ops on
this surface that can lose DATA**. Each of the three ships behind two things nothing else here
has: a **cross-table loss preview** produced in the dry run, and an **explicit-consent fence**, so
none of the three is reachable from a default call. The blast radius of each is stated in its own
row, because they are not the same size. **`delete_view` is deliberately NOT one of them, and the
empty `DESTRUCTIVE_OPS` in its family says so rather than omitting the name**: a view is a saved
presentation — a filter, a hierarchy pointer, a hidden-field set — so its delete destroys
**configuration and not one cell**, which leaves no loss to enumerate and nothing to consent to.
It is still plan-gated and still verified by read-back; what it has no need of is a preview.
**Deleting the Base itself is still not a REGISTERED SCHEMA OP** — and the reason is kept while
the tail of the old conclusion falls. The reason: it removes the Base rather than something
inside it, so it has no descriptor, no plan-time loss preview and no consent token, and the
drive-file delete remains the whole-object gate rather than a fourth shape on this table. What is
**superseded** is the sentence that used to follow it — *"the drive-file delete stays a
live-harness primitive, and nothing offers a consumer a one-call `delete this Base`"* — which
LD-466 falsified: `delete_base` ships as a **lifecycle** call on this client, documented in its
own table below the fifteen, and a consumer does now get that one call.

**A PLAN-WIDE PLATFORM ANOMALY HALTS THE APPLY — the one place a schema apply stops on a code
neither ruled table knows (LD-337 detects, LD-338 halts).** The entry-scoped/systemic split (D4′)
is judged **per exception** and is untouched: an unmodelled Lark code is still `api-error`, still
entry-scoped, and still lets the batch continue. Above that classifier the engine now judges one
**plan** question the classifier structurally cannot see — when **every call this plan has
attempted** (at least two, `PLATFORM_ANOMALY_MIN_ATTEMPTS`) refused with the **same** code
**neither** `SYSTEMIC_CODES` nor `ENTRY_SCOPED_CODES` carries, on table ids **this run's own read
client listed**, the remaining entries are not attempted. Six conjunctive conditions, one
predicate (`disposition.plan_wide_platform_anomaly`), evaluated at two moments: over the prefix
while entries remain, and plan-wide at the end for the disclosure. An entry that **applied**
anywhere disarms it permanently, and plan-time-refused or `stale` entries never count toward the
floor — Lark never judged them. `apply-log-complete` holds: the log stays 1:1 with the plan, in
plan order, and each skipped entry says the anomaly was the cause, that nothing was sent, and what
a re-run does. **No retry, no backoff, no re-probe, and the halt decision itself makes no extra
call** — LD-329 measured that a `9499` on this route does not clear between entries (0/30/60 s,
+~30 min, +3 min, +4 h). The 2026-08-07 `/fields` outage is the incident this exists for; the
shipped `permission-denied` halt is the doctrine it follows.

**THE LOSS PREVIEW IS APP-SCOPED, and the evidence forces it.** Deleting a `DuplexLink` (type 21)
column deletes its **mirror column in another table** (`p0-2-07`, and symmetrically `p0-5-02`);
deleting a **table** is a different route (`DELETE …/tables/:table_id`, measured on its own —
row 32), and it ends the two kinds **differently**, both **silently**: an inbound `SingleLink` in
**every other table** *survives and dangles* — `property.table_id` still names the dead table,
`table_name` drops out, the cells keep the record ids, and `records/search` stays `code:0` with no
error anywhere — while an inbound `DuplexLink` *does not survive at all*, its twin living inside
the doomed table and the source column going with it. And
the dependency is not only the link graph: deleting a table **blanks every `Lookup` column that
mirrors it**, in every other table, on every row — the column survives, its configuration still
names the dead table, and nothing errors. So the preview reads **every table's columns** before
anything is deleted and names both columns, both tables and the cell counts of each — plus every
Lookup mirroring a doomed table, at no extra call, refusing outright on a Lookup whose own
configuration does not say which table it mirrors. **A loss that cannot be enumerated REFUSES** — register row
32, the Sheets structural rung's invariant widened from one sheet to the whole app.

**A `property` shape no capture carries is a GUESS, and is refused rather than sent.** The

invented key would answer `code:0` having authored a column without it.

#### View writes — the persistent filter, and FILTERS ONLY

**The view lifecycle ships, and what it ships is a filter.** `POST …/views` ·
`PATCH …/views/{v}` (`view_name` and `property.filter_info`) · `DELETE …/views/{v}`, all
plan-gated, with `GET …/views` from the read floor. A filter set through this library is the
filter a human sees when they open the Base: conditions **`field_id`-keyed** with **camelCase**
operators, `code:0`, and the filter **reads back fully persisted**.

**The `view_type` allow-list is evidence-keyed in both directions.** `grid`, `kanban`, `gallery`
and `gantt` were each created `code:0` (`p0-3-01`); `calendar`, `board` and `list` are each
refused **`99992402` by the server**, whose `error.field_violations` body carries the accepted
list verbatim — *"view_type is optional, options: [grid,kanban,gallery,gantt,form]"* — so this
library refuses those three **locally, in the server's own words**, rather than spending a round
trip on a refusal it can already quote. `form` is in Lark's list and **not** in larkdocio's; the
row below says why, and it is a policy row rather than a capability one.

**Nothing here is verified by `code:0`, and this rung has the negative control that proves it.**
The same `PATCH` that persists a `filter_info` **silently discards** a `group_info` — `code:0`,
and the view reads back `property: null`. So the engine **re-reads the view** and compares the
persisted `filter_info` against what it sent, semantically: the server adds `condition_id` and
echoes `field_type`, and those two keys — and only those two, by name — are normalised away
before a whole-value comparison. A `code:0` whose read-back does not echo is reported
**not persisted**, never `applied`.

**There is NO anchor for a view write, and every plan entry says so.** No capture carries a view
revision, and what `table.revision` does in response to a view `PATCH` was never measured — so
no compare-and-swap is built on either and none is implied. The one authoring of that absence is
`larkdocio.base.schema_ops_views.NO_VIEW_ANCHOR`, and it is a **different** fact from register
row 28's (`app.revision` counts inconsistently) and row 25's (`table.revision` and the ignored
precondition keys).

**The two filter dialects are made uncrossable BY CONSTRUCTION.** `records/search` filters are
`field_name`-keyed; **view** filters are `field_id`-keyed — and, measured live in this story,
the two **also encode a value differently**: `records/search` takes a real JSON array
(`"value": ["Text 1"]`, `[]` when the operator takes none), while the view route takes a *string
carrying* a JSON array (`"value": "[\"Text 1\"]"`, `code:0`, reads back verbatim) and requires
a valueless operator to **omit the key entirely** — `""` answers `1254001`, `[]` answers `9499`,
and omitting it answers `code:0` and reads back `value: null`. Two differences, one per
serialiser. `larkdocio.base.view_filters` ships one model and two serialisers, each producing
its **own non-forgeable type**, and the view route's own signature accepts only the view type —
so there is no expression that sends one dialect to the other's route. A field **name** is resolved to its id locally against
`GET …/fields` **paged to exhaustion**, an unresolvable name is a typed refusal naming the
table's fields, a `field_id` the caller supplies is passed through unresolved, and a **truncated**
field read refuses to resolve at all.

### The guided column-type migration — `larkdocio.base.field_migration`

**The conversion refusal is unchanged, and it no longer leaves you to rebuild the column
unsupervised.** `convert_field` still refuses every pair no capture covers — the pair table is
still exactly `Text -> Barcode` — because a cross-storage-type conversion rewrites every value
server-side, permanently, and nobody has watched it happen. What changed is what a consumer does
next. *"Change a text column to a number"* used to mean hand-writing **create a new column → copy
the values → DELETE the old one → rename the new one**: a sequence whose destructive middle step
is fenced beautifully and whose **ordering nothing enforces**. Get the order wrong, die between
the copy and the delete, or let a value the target could not encode slip through, and data is
stranded with every shipped guard still green.

`plan_field_migration(...)` / `apply_field_migration(...)` make the **sequence** the unit:

- **One plan, five steps, in apply order** — create the staging column, copy the re-encoded
  values, **read the copy back and compare it**, delete the source column, rename the staging
  column. The consumer never assembles the sequence and never chooses the order.
- **The preview costs zero writes** and no write client is even accepted by the planner. The
  destructive step carries the **existing** loss preview (`cells_with_data`, the inbound
  enumeration) unchanged.
- **Consent is the existing primitive, bound to the migration plan.**
  `consent_to_destroy(migration_plan)` mints the same `DestructiveConsent`, from the same private
  token; the delete step then re-previews immediately before destroying and **refuses on any
  difference** from what was consented to.
- **The delete is unreachable on an unverified copy.** Every value is read back out of the
  staging column and compared to what was sent; any mismatch, any count difference, halts with a
  typed refusal and the source column standing. *The copy did not round-trip* ⇒ nothing is
  destroyed.
- **A value the target kind cannot encode refuses the WHOLE migration at plan time**, naming the
  records and the values. There is no lossy mode, opt-in or otherwise: guessing on your behalf
  would mean guessing about every value in the column.
- **It is not a conversion, and it says so** — a conversion is a server-side rewrite nobody
  observed; this is a client-side rebuild in which every value passes through the caller's own
  process. `convert_field`, `CONVERSION_PAIRS` and `enabled_conversion_pairs()` are untouched, and
  the migration is not registered as a pair.
- **It cannot be atomic and does not imply it is.** Several HTTP calls across two engines, no
  transaction to wrap them in. What it promises is an **account**: one log entry per step, in
  plan order, each ending in a typed disposition, remaining steps logged `not-attempted` after a
  halt — and a halted run's log naming which columns exist, where the values are, and what a
  recovery would do. Because the destructive step is gated on the verification, a partial run
  leaves a table with an **extra** column, never one with a missing one.

**Error taxonomy.** Every code the three packs observed maps to a typed error with an

### The opt-in RAW value view — `read_base(url, retain_raw=True)`

Everything above this line is **display-shaped**, and that is the right default: one renderer,
one opinion, clean deterministic Markdown. The cost is invisible until someone tries to
*compute* with the output — a Date leaves as `2025/07/01`, an Email as
`[you@example.com](mailto:you@example.com)`, a Person as a comma-joined name — so a dedupe, a
diff, a compare or a chart has to parse the library's own Markdown back apart, or re-read the
table and do the whole job again. **The payload it wants was already received**: the record's
`fields` body is in `assemble_table`'s hand on its way into the renderer, and was dropped at
the end of the loop. `retain_raw=True` keeps it.

**Raw is the wire shape, byte for byte** — no key renamed, no absence coerced, no epoch turned
into a string, no list flattened or sorted, no type changed — and it is deliberately **not** a
normalized typed middle form. No `datetime`, no `Decimal`, no person class, no `to_python()`,
no per-type converter: a third value vocabulary after the wire's and the renderer's is one this
library would have to define for every type, defend when Lark's shapes drift, version, and be
wrong about at exactly the moments precision matters. It is **evidence, not a model**.

| Property | What holds | Code anchor |
|---|---|---|
| **Opt-in, and OFF is byte-identical** | the rendered output of `read_base` / `read_base_markdown` / `snapshot_table` does not move, and **nothing is retained** | `larkdocio.base.table.assemble_table` |
| **Zero new API calls, either way** | the flag decides whether an already-received payload is kept, never whether one is fetched | `larkdocio.base.read.read_base` |

### The per-table REVISION — the change-detection anchor the read already fetched (LD-333)

`read_base(...).tables[i].revision` is the `revision` that table's `GET …/tables` entry carried.
**It costs no extra call and no extra scope**: the read already receives that reply as the second
of its five, and until LD-333 the number was destructured away one tuple element wide. It is the
same field the write engine reads as its compare-and-swap anchor — *"the **only** compare-and-swap
anchor bitable exposes"* (`larkdocio.base.apply`) — now visible on the read side too, so a
consumer's ingestion ledger can change-detect a Base instead of recording `revision=unknown`.

**What the number means — four facts, each already measured by this surface, none re-derived here.**

| Fact | What holds | Code anchor | Evidence |
|---|---|---|---|
| **Per-table isolated** | an edited table advances while an **untouched sibling stays put**, and the **app revision** does not move at all (`05-08`: `18 → 19` on one table, `0` on the other) — which is why there is deliberately no Base-level number | `larkdocio.base.plan` | `tests/captures/base-study/captures/05-08-staleness.json` · `tests/test_base_read_revision.py` |
| **An OP counter, not a row counter** | a field create is `+1` and a field delete is `+1` (`12 → 13`, `14 → 15`) — one op, one bump — so a post-write expectation of `+N` per row is wrong | `larkdocio.base.field_authoring` | `tests/test_base_md_matrix.py::test_row_26_states_the_BATCH_CONTRACT_QUOTED_from_the_code` |
| **`0` is a real value; `None` means "not known"** | a freshly created Base reads `0`, and the standing Scratch Base read `0` before moving to `14` and then `30` — so an absent revision is `None` and is **never** synthesized to `0`, and the two stay distinguishable | `larkdocio.base.table.BaseTableRead` | `tests/test_base_read_revision.py::test_ac2_an_ABSENT_revision_reads_None_and_the_TWO_ARE_DISTINGUISHABLE` |
| **There is no `If-Match`** | this API ignores a precondition body key, so the revision is an **observation** — any guard on it is client-side **read-compare-write**, exactly as the writer's `STALE_TABLE` halt is built | `larkdocio.base.apply` | `tests/captures/base-study/captures/05-08-staleness.json` |

**The limitation, stated rather than papered over.** Because the anchor is per **table**, a Base
with **no tables** gives a ledger nothing to compare, and so does a change that moves no table's
op counter. A consumer must read "nothing to compare" as **unknown**, never as *unchanged* — that
is the wrong-skip this passage exists to prevent.

**No Base-level or app-level revision is invented.** The app revision was probed and does not move
when a table's does; a max, a sum or a hash over the per-table set would be a derived number
presented as an API fact. A consumer who wants one computes it from the set this surface now hands
over.

**`read_base_markdown` deliberately does NOT print it.** The Markdown is the reading form and a
version is a fact about the read, not a line of the document — printing it would move bytes every
consumer's diff depends on. The projection stays lossy on purpose, the same ruling the raw-value
view took: **take `read_base` for the version.** Said in both docstrings
(`larkdocio.base.read.read_base_markdown` names it) and pinned by
`tests/test_base_read_revision.py::test_ac4_read_base_markdown_DELIBERATELY_does_not_surface_the_revision`.

| Property | What holds | Code anchor |
|---|---|---|
| **Zero new API calls** | still *"five reads per Base, and not one more"* — a call-count spy is the fence | `larkdocio.base.read.read_base` |
| **Zero new endpoint, zero new scope** | `GET …/apps/:app_token/tables` was already called and already carries its `larkdocio.permissions` row; the op set is unchanged | `larkdocio.base.ops` |
| **Zero rendered drift** | the Markdown is byte-identical to the committed golden of the whole captured Base | `larkdocio.base.table.render_base` |
| **Not behind a flag** | it costs nothing to be right about, so it is always present — the same reasoning as `link_columns` | `larkdocio.base.table.BaseTableRead` |

## Comments

A Base's comments are **not** part of the Base API at all: they are listed by the **drive**
comment family, the same one a document's are, with the Base's app token as the file token
and `file_type=bitable`. So they reach a consumer through the shipped comments surface
(`larkdocio.comments`) rather than through the Base client above — **one comments client,
one entry point, a third accepted file type.**

The read half **can name the row**. Each reply carries `extra.notify_extra`, holding the
record, table and view the reviewer had open — surfaced as structured data on the thread and
on every reply, with a named `file-level` state for a comment that names no row. **Two
payload facts shape the implementation and are worth knowing before you build on it:** the
wire keys are `record` / `table` / `view` (the shorter spellings — the ids are what the
longer ones would have meant), and the pinned SDK's `ReplyExtra` models only `image_list`,
so the object is read from the same response's own bytes — **no second call, no second
client, no second HTTP path.**

| Capability | Status | Where it lives | Evidence |
|---|---|---|---|
| `comments.read` on a Base — the file-level list, **record-attributable** via `extra.notify_extra` (`record` / `table` / `view`), with a typed `file-level` state and the documented empty state | `supported` | `larkdocio.comments.comments` (`file_type="bitable"`) · `larkdocio.comments.attribution` | `tests/captures/base-study/captures/p1-q7-01-comments-populated.json` (the populated list, captured read-only) · `tests/captures/base-study/captures/p1-q4-01-comments.json` (the empty state) · `tests/test_base_comments_read.py` |
| `comments.write` on a Base — creating, editing, resolving or deleting a comment, at every granularity | `refused-by-server` | no path is exposed; `larkdocio.comments.BASE_COMMENT_WRITE_REFUSED_NOTE` states the refusal | create answers `99992402` naming its own list, `options: [doc,docx]` — `bitable` is absent; a record id as a file token is `1069307 not exist`; `file_type=bitable_record` is not in the read enum either; `…/records/{r}/comments` and `…/tables/{t}/comments` answer the gateway's non-JSON 404. `tests/captures/base-study/captures/p1-q4-01-comments.json` · `dev/base-study/ui-parity-matrix-2026-08-03.md` § 4 |

**PII.** A comment thread is a new payload class for the name-only doctrine: it carries
commenter identity and may carry @mentions. The payload gives **no** name — an author is an
opaque id and nothing else — so a rendered thread labels every person with a redacted marker
and never an id, an address or an avatar, while the structured projection keeps the raw id
for a consumer that can join it to a real identity.

## Column shaping — grouping and field ordering, classified

Two more consumer questions, both measured by LD-417 against four disposable Bases the spike
created and deleted (`dev/base-authoring-spike/findings.md` § Leg A, § Leg B — in the dev
repo). Neither is a row in the tables above: **grouping** has no route to type a row against,
and **ordering** is a mix of a shipped answer and a measured refusal that does not fit any
single table's status column, so both are stated here as prose instead. **No code and no
parameter changed for either** — this section documents what was measured, not a new
capability.

**Column / field GROUPING has no API route.** The subject is grouping COLUMNS in the table
UI — the feature a consumer works around today with column-name prefixes like `P0 - Not
started`. It is **NOT** view **record** grouping (rows bucketed under a field's value), which
is `property.group_info` and is a different feature with a confusingly similar name — see
register row 2 above and the guide's **Recipe: create, configure and delete a view — hidden
columns ARE settable; grouping and a saved sort are NOT**. Conflating the two is how a
reader concludes the wrong thing from either measurement. **20 group-shaped attempts** across
the only three shapes that could carry it — the three counts below sum to it — **plus the
three named controls they were each read against** (a positive table rename, and an
invented-key control on the table route and on the field route): the **table** route
(`PATCH …/tables/{t}`) answers `1254001 "The request body cannot be empty."` for all **7**
group-shaped keys tried — `field_groups`, `column_groups`, `groups`, `field_group_info`
top-level, and `property.field_groups`, `property.column_groups`, `property.group_info` —
**byte-identical to the invented-key control**; the **field** route (`PUT …/fields/{f}`, each
arm riding a genuine rename so the call could not be a no-op) accepts all **8** group-shaped
keys tried — `group_id`, `field_group_id`, `group_name`, `column_group` top-level,
`property.group_id`, `property.group_name`, and `group_id` / `field_group_id` at field-create
time (`POST …/fields`) — with `code:0` and **stores nothing**, identical to the invented-key
control, so the acceptance is **attributable** rather than a guess; and **5** dedicated
endpoint spellings — `…/tables/{t}/field_groups`, `…/tables/{t}/fields/groups`,
`…/tables/{t}/column_groups`, `…/tables/{t}/groups`, `…/apps/{a}/field_groups` — answer
**HTTP 404** with no Lark envelope at all. Two structural facts matter more than any single
arm: a `PATCH …/tables/{t}` body carrying only unknown keys is answered **empty** (it parses
`name` and nothing else), so there is no table-level property envelope for a group to live
in; and a field's read model carries **no group concept in any spelling** — `field_id,
field_name, is_extend, is_primary, is_synced, property, type, ui_type`. A feature the read
model cannot express is not one the write model is hiding. **Not tried** (unmeasured, not
refuted): `user_access_token` (every call here used a `tenant_access_token`); the web
client's own product-internal endpoints; any `bitable/v2` spelling (none is documented —
inventing a version prefix measures the router, not the feature); the Base **dashboard**,
**automation** and **form** families; `POST …/apps/{a}/copy` from a template that already
has groups; and whether a **non-grid** view type (kanban / gantt / gallery) exposes a
column-group vocabulary a grid view does not. **Scope of the claim** (the scope-of-evidence
doctrine, D-59): this grounds *"there is no column-group route on bitable v1 for a tenant
token"*, **not** *"Lark cannot group columns"* — the product UI plainly can.

**Column ORDER is settable — once, at table creation, and nowhere else measured.**
`create_table(app_token, name, fields=[…])`'s `fields=` array **decides the column order**:
proved with a reversed control, two tables in one Base, the same three names in opposite
orders — `["Zeta","Mu","Alpha"]` and `["Alpha","Mu","Zeta"]` — each reading back in its own
array's order. (Register row 47 above already established the array's *first* entry becomes
the table's primary column; this is the general case the same measurement makes.) **After
creation, no route places or moves a column, measured**: **12** create-time position
spellings — `index`, `position`, `field_index`, `order`, `column_index`, `insert_index` (as
`0`); `pre_field_id`, `after_field_id`, `insert_after`, `insert_before` (as an existing field
id); `?index=0` as a query parameter; plus the invented-key control — all answer `code:0` and
all **append at the end**, identical to the control; **5** update spellings — `index`,
`position`, `field_index`, `column_index`, `pre_field_id`, each riding a genuine rename —
answer `code:0` with the rename landed and the order **unchanged**, identical to the control;
and **6** move/reorder routes — `POST …/fields/move`, `…/batch_move`, `…/sort`, `PATCH
…/fields/sort`, `PUT …/fields`, `POST …/fields/batch_update` — answer **HTTP 404**, no Lark
envelope. So the honest sentence is not *"column order is not settable"* — it is *"column
order is settable **once**, at table creation, through `create_table(..., fields=[…])`; after
that a column cannot be placed or moved by any route measured."* **Not tried:**
`user_access_token`; the web client's internal endpoints; a **non-grid** view type's own
property vocabulary — this one matters, because kanban/gantt views are exactly where a
field-order property would plausibly live, and only a grid view was probed; deleting and
re-creating columns to force an order, which is a **data-destroying rebuild**, not an
ordering route, and was **deliberately** not probed; `POST …/apps/{a}/copy` followed by
re-authoring.

**AND THE ROUTE THAT SETS THE ORDER IS THE ROUTE THAT REFUSES TWO KINDS — the two facts
collide, and LD-473 states the cost.** `create_table(..., fields=[…])` will not author a
**`Checkbox`** or a **`Rating`** (register row 47's neighbour: Lark answers `1254012
"Unsupported field type."` and creates **nothing at all**, probe `ld336-02`), and it is the only
route that sets order. So a table needing one of those kinds at a chosen position cannot have
both, and the consequence — **`create_field` appends, so the position is forfeited
permanently** — is what the enumeration above means in practice. **The workaround is real and it
is a demotion, not a cure: APPEND ORDER IS DISPLAY ORDER**, measured with an anti-alphabetical
control (probe `ld473-01`): a table created with the kit `["ld473-title","ld473-score",
"ld473-when"]` read back in that order, then `ld473-open` (a `Checkbox`), `ld473-zeta` and
`ld473-alpha` appended one `create_field` call each read back as `[title, score, when, open,
zeta, alpha]` — **call order, at the end, moving nothing that was already there**, which rules
out server-side name sorting. So: author the orderable prefix with `fields=`, then `create_field`
the refused kinds in display order; everything the create route refuses sits after everything it
accepted. *Evidence:* `tests/captures/base-study/captures/ld473-01-seeding-and-append-order.json` ·
`tests/test_live_base_schema_gate.py::test_arm6_A_NEW_BASE_IS_SEEDED_and_a_LATER_COLUMN_IS_APPENDED`.

**A CREATED BASE IS SEEDED, AND `list_tables(app_token)[0]` IS LARK'S TABLE.** Measured on the
same disposable (probe `ld473-01`): `POST …/apps` answers a Base already holding **one table
named `Table`**, carrying **four columns** — `Text` (primary), `Single option` (`SingleSelect`),
`Date` (`DateTime`) and **`Attachment`** — and **ten blank rows**; the create's echo names it on
`default_table_id`, and that id is what `list_tables(app_token)[0].table_id` returns. Tables the
caller creates are **appended after** it. This is Lark's behaviour, not this library's, and no
code path here deletes or hides it — removing it is an ordinary plan-gated `delete_table`. What
is guarded is the **disclosure**: the shipped guide states the shape where the create is taught
and at every site that indexes `[0]` on a Base it just made. Should Lark change the seeding, the
shape is what goes stale — read `list_fields` on that table rather than trusting the four names.

*Evidence:* `dev/base-authoring-spike/findings.md` § Leg A, § Leg B (in the dev repo) ·
`dev/base-authoring-spike/captures/ld417-a-01-column-groups.json` ·
`ld417-ab-02-attributable-field-update.json` · `ld417-b-01-field-ordering.json` ·
`ld417-b-04-create-time-field-order.json`. Minted at **D-66** (`requirements/DECISIONS.md`),
citing **LD-425** and **LD-417** together.
